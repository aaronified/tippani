# ADR-0266: A grade is kept on the device and sent until the server takes it

Source of truth: this wiki page.

- **Area:** [§8 The Review Loop](ADR-Index.md#area-8)
- **Status:** Accepted
- **Version:** Unreleased

**Decided.** Every quiz answer, Daily and Practice, is written to this browser's storage the moment it is given (`answerQueue.js`, keyed per reader), and the card moves on at once with nothing on screen about sending. One sender posts the kept answers in the order given and drops each only when the server has answered: a 2xx takes it; a 4xx other than 401, 403, 408 and 429 drops it (sending again would be refused again); a 401 or 403 (signed out, or the password an admin chose still standing) keeps it and waits with no clock for the next start of the app, return online, return to the tab or new answer; and anything else, a network failure included, waits 2 s, doubling to a minute, and tries again, as do those same events. The app sends nothing while an admin-chosen password stands, and sends at once when the reader has chosen their own. Each answer carries an id the browser made and how long ago it was given. The server keeps the id in the recall log (migration 0080) and answers an id it already holds with the state as it stands, writing nothing; it files the answer at `now − ago`, on that day's tally and streak, and an answer older than the card's last review is logged but moves no schedule. The Daily card leaves out of its deck the card of any answer the deck was drawn without: one still kept, or one this page sent after the deck was asked for (the app asks for the deck and sends kept answers as it starts, and either reply can land first). Such an answer counts in today's tally and the streak, if it was given today, and moves its card in "where you stand"; a card the deck no longer holds was answered on the server's side and is in its counts already, so nothing is counted twice. After the oldest kept answer has waited a minute, one line under the card says how many are waiting. A typed blank waits at most three seconds for its mark, because the server grades it; past that the card says "kept, to be marked" and Next works, and a mark that arrives while the reader is still on the card replaces it.

**Why.** The owner, 1 October: "this saving thing is often a long thing … If i click next at this point, it progresses without saving and then after the quiz is over it again comes back on page refresh", and, of a round where four of five answers reached the server, "Now on page refresh, that will come back." The entry above made Next always work and accepted losing the grade as "a small cost"; the owner's report is what that cost looks like, a card asked twice and a score short. The owner asked for "the whole quiz [to] be recorded before syncing … That way the sync will not even be visible to users … make sure that the sync keeps on retrying."

**Instead of.** A server job, the owner's first idea ("Can this be a job"): the answer that goes missing never reaches the server, so nothing the server runs can recover it, and the jobs queue is for work that outlives a press, not for one row. A timestamp in place of the age: the browser's clock may be wrong, and the age needs only the clock to run at the right speed. Holding a Practice repeat to the same-day echo the Daily mode already had: Practice answers the same card several times a day by design, so only an id can tell a repeat from a resend.

**Got wrong on the way.** The first sender fell back to its in-memory copy whenever storage had no key, so after another tab sent the last answer and removed the key, this tab brought the sent answers back. The dom test found it by leaking one test's answer into the next. Memory is now used only when storage throws. A rating then found three more, all fixed. The deck was filtered by the answers still kept when it arrived, so a deck asked for before a send and answered after it dealt the answered card again; it is filtered by what this page sent too. A typed blank waited on the send itself, up to its twenty-second timeout on a congested network, which held the reader exactly where the owner said it must not. And the password gate's 403 was taken for a refusal of the answer, so a reader whose password an admin had reset lost every kept answer the moment the app opened.

**Approved.** The owner agreed the design on 1 October ("i agree with your suggestion").
