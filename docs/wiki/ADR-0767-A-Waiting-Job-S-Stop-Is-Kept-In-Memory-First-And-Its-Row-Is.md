# ADR-0767: A waiting job's Stop is kept in memory first, and its row is written after

Source of truth: this wiki page.

- **Area:** [§18 Jobs and Logs](ADR-Index.md#area-18)
- **Status:** Accepted
- **Version:** 3.1.0, corrected after its release

**Decided.** A Stop, a Stop all or an account's delete that reaches a waiting job marks it stopped in the queue's memory and answers. The row goes from waiting to stopped once SQLite's write lock can be had. The press itself tries for the lock for 50 ms. After that the worker writes the row before its next claim, the running job writes it after its next progress write, and shutdown writes it before it interrupts whatever still waits. And every swap of the database files — a restore, a recovery, a factory reset — writes it into the file it is about to move before it moves it, waiting for the lock as any write does; a swap that cannot is not made, and says so (`TIP-JOBS-002`). A Stop reads and marks its waiting jobs with no swap under way, and one pressed while the files are being swapped is refused at once as a press from before the swap. From the press on, no claim that begins takes the job, and one already waiting for the lock that takes it anyway stops it before its first step, because a write of the row that finds it taken leaves the mark for the worker to find; an Enqueue's duplicate and limit checks do not count it, nothing counts it as ahead of anybody, and `GET /jobs`, `/jobs/{id}`, `/jobs/summary` and `/jobs/common` read it as stopped at the moment of the press. Stop all and an account's delete read the running rows in their scope rather than write them, and set the running rows' `stop_requested` flag only if the lock can be had within the same 50 ms.

**Why.** My ask for the kill switch, *"the job cancel button must also be the most responsive kill switch. No dillydallying after it has been pressed"*, covers a job that has not started yet as much as one that has. A waiting job's Stop was its row's write, and a running import stages its whole file in one transaction, and an approval writes each work in one. A Stop on the job waiting behind either of them waited for that transaction, and past busy_timeout's five seconds it answered an error. Telling the running job first (*An import and its approval are queued jobs*) does not help here, because the running job is not the one being stopped. Holding the waiting jobs before the running one is cancelled also closes a gap. The running job, cancelled at the press, could end and let the worker claim the next of the same viewer's waiting jobs before Stop all had stopped it. The swap writes the rows because a mark is kept for the generation it was made in (*A generation guards every owner across a file swap*), so after a swap it speaks for nothing, which is right for a file where the same id may be another job and was wrong for the job itself. While a restore holds the queue no worker is alive to write the row, so a Stop whose own 50 ms missed the lock was still only a mark when the swap came. Its row went on into the restored file still waiting, and the carry-over marked it interrupted, though its reader had been told it was stopped. After a recovery, or a restore that failed and put the old file back, the row was simply waiting again, and the job ran once the queue opened. Pressed mid-swap, a mark could be made after the swap had written the others and before it closed the file, and be lost with it.

**Instead of.** Carrying the marks across the swap, which would stop whatever job holds the same id in the file brought in: a factory reset starts the ids again, and so can a restore whose carry-over failed. A swap that goes ahead when the rows cannot be written, which is the same loss on a rarer day: the lock held that long is a writer outside the server, and the restore can be pressed again once it lets go. A Stop mid-swap that waits for the swap to end, only to be refused then, since its account and its ids belong to the file that moved. Waiting out the lock, as the Stop first did. A goroutine per Stop that retries the write until the lock frees, which would be a third goroutine outliving the call that starts it (§1). The mark alone, with the row written only when the job would have been claimed: a restart before that would find the job waiting and mark it interrupted, and the duplicate check would go on refusing the same job pressed again.
