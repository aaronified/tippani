# ADR-0785: Every backup queues, and the safety copy is handed over once

Source of truth: this wiki page.

- **Area:** [§18 Jobs and Logs](ADR-Index.md#area-18)
- **Status:** Accepted
- **Version:** 3.1.0

**Decided.** `POST /admin/backup` is the same enqueue as `POST /jobs {kind: "backup"}`: its body is the job's params, a missing credential or a short passphrase is a 400 and a password that is not the caller's a 401, both before anything waits, and then it answers 202 with the job, whose result is the archive `GET /admin/backup` describes. The same backup asked for at either address while one waits is one job. The safety copy a restore or a reset takes first is a queued job of kind `backup.safety`: `POST /admin/backup/safety` checks the credential the same way and queues it, and the job seals the copy into `<data>/.safety-<random>.tpbk` — a control entry, so no backup made while it waits carries it and no restore moves it, and never in `backups/`, which the Server card lists and a restore from the server reads. The job's result names a one-time download, `GET /admin/backup/safety/{token}`: only the admin whose job sealed it may fetch it; another admin or a reader is answered 404, as a token that names nothing is, and a request with no session is stopped at sign-in with a 401 before the token is looked at. The first GET that is let in spends the token and removes the file when it ends, and a HEAD is refused, so a tool that asks the size first spends nothing and lets nothing go. It waits five minutes. A new copy replaces its owner's earlier one, a restore, a factory reset or the owner's deletion drops every copy still waiting, and the server's start removes every `.safety-` file. The safety note that lets a restore or a reset go is set only when a download has sent the whole file, as it always was. A Stop lands where a backup's does — before the snapshot, between files, inside a file's copy, and last just before the copy is published — and a stopped copy leaves no file and no download. The copy's job is not offered Run again: a copy is taken for the prompt that asked for it. The token is blanked from every kept request line, as a share link's is. In the app, the first step of the restore and the reset prompts asks for the copy, says where its job stands in Current jobs' own words — waiting, with how many are ahead, then being sealed — beside a Stop that ends it, and downloads the copy as soon as the job has sealed it; only then does the prompt's next step open. A Stop, a failed job or a refused download gives the button back with the reason, and downloads nothing.

**Why.** My answer of 28 September, that imports and every backup queue (F1). The API's backup sealed its archive in its request, and the safety copy streamed one into the response, each beside whatever the queue was running and past any Stop. And the copy cannot simply become a backup: the server keeps one archive, and a copy kept among the backups would be what the next restore from the server restores — the copy of what it is about to replace (*Two more gaps closed before 3.0.0*).

**Instead of.** A timer that deletes a copy the moment it expires, which my invariant rules out (*nothing wakes on a timer*): a copy past its time is let go of the next time the copies are looked at — another copy published or asked for, a download, the Server card's read — and at the next start. So a copy nobody fetched can sit on the disk past its five minutes until one of those happens, and never past the next restart. A download that stays open for as long as the token lives, which would let a fetch cut short be tried again, and would make "once" mean "until it expires". Letting `POST /jobs` queue a safety copy, or Past jobs run one again: the copy is a step of two prompts, and a copy nobody is waiting for is a whole library on the disk.
