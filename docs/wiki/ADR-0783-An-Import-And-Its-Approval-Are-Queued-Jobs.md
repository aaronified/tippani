# ADR-0783: An import and its approval are queued jobs

Source of truth: this wiki page.

- **Area:** [§18 Jobs and Logs](ADR-Index.md#area-18)
- **Status:** Accepted
- **Version:** 3.1.0

**Decided.** Every import route — the drop target's `POST /import/auto` and the eight per-source routes — reads the upload in its request (the 5 MB cap and an unknown "Read this as…" format are still refused there, with a 400), keeps the bytes as a file under `<data>/.jobs-spool/`, queues a job of kind `import` naming that file, and answers 202 with the job. The job stages the file as the request used to and keeps, as its result, the status and body the request used to answer; the Import screen follows each file's job — "Waiting — 2 jobs ahead" while it waits — and reads that result exactly as it read the request. `POST /import/staged/approve` checks the selection in its request (400, 404) and queues a job of kind `import.approve`, named after the file its quotes came from; Pending import follows it with its progress and a Stop, and reads the queue again when it ends. The press fixes what the approval may take: the newest batch Pending import drew (`through`, which Approve all and Discard all send), or the newest there is when the request names none, never a newer one; the job, and a Run again of it, approves nothing staged after that. Batch ids come from the id floor, so a batch approved or discarded meanwhile cannot hand its id to the next file. Neither kind is startable through `POST /jobs`, since each names rows or a file its own route checked. A Stop is heard at each kind's own steps, since neither looks outward: an import as its job is claimed, between the works it stages and just before its staging commits — the whole file is one transaction, rolled back — and an approval before each work and just before that work's own transaction commits, so every work before a Stop is in the library and the one in hand and every one after it are still staged. The spool is never archived or moved by a restore. A staging removes its file just before it commits, and a refused file goes once it has its answer; a stopped or interrupted import keeps its file and is offered Run again while the file is kept, until a restore carries it over (*A job a restore carried over is its history*); everything else is swept at start, after an account's delete, after a factory reset and a restore, before each upload and after the prune, and a sweep that comes while the files are being swapped reads nothing and keeps everything, since the file open then may be a restored one the server's jobs have not yet been carried into. And a Stop, a Stop all and an account's delete stop the job in hand — its flag set and its context cancelled, as *Stop is at once, and it breaks nothing* has it — before they write anything themselves, because each of those writes waits for SQLite's write lock and an import in its transaction is the one holding it.

**Why.** My ask of 28 September for Settings → Jobs: *"If any eligible action is run, a job will be created and queued … No action should skip through"*, and my answer to the question that followed, that imports and backups queue. An import ran beside whatever the queue was running and could be neither seen waiting nor stopped, and the approval — the one import step that writes to the library — left no row at all. And my rule for a Stop, *"it still shall not break anything"*: a Stop that lands mid-file stages none of it and keeps the upload, so nothing is lost and nothing is half-written.

**Instead of.** The bytes in the job's params, which every list of jobs and every duplicate check would read, five megabytes at a time. One transaction for a whole approval, as the request had it, which would hold the write lock for a library-sized export and roll all of it back on a Stop; so a failure part-way now leaves the works before it approved, and the answer says so. Removing a stopped import's file, which is what the first cut did, and which made a Stop on a waiting import lose the upload. Reading an approval's selection only when it runs, which is what the first cut did too: an "Approve all" pressed while a file waited its turn, or run again a week later, put quotes in the library that nobody had seen in Pending import — the thing the queue exists to prevent. Sending a batch of files one at a time, each after the last had run, which behind a two-hour fetch would keep one file on the server and the rest in a tab that could close: each file is sent as soon as the queue will take it (five of a reader's jobs at a time) and queued as its upload lands, so a closed tab keeps every file already sent, and a file not sent yet is still only in the page, which its row says.
